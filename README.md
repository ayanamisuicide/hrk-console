# heroku-console

Консоль для Telegram-юзербота [Heroku](https://github.com/coddrago/Heroku): запуск, остановка и живой просмотр логов из терминала.

```
╭─ HEROKU ──────────┬──────────────────────────── ● live  2.2.2  ·  1ч 12м ─╮
                    │
 М О Д У Л И        │ 00:13:01  INF   terminal   Command .sh executed by 827…
 tl_cache █████  12 │ 00:13:04  WRN   spotify    Token refresh took 4.2s
 spotify  ███▎    5 │ 00:13:07  ERR   tl_cache   Failed to resolve @unknown  ×12
 terminal █▋      2 │                          ↳ PeerIdInvalidError: could not…
                    │ 00:13:20  INF   spotify    now playing: Radiohead — Creep
 П О Т О К          │
 ▁▂▅▇▃▁▁▂▆▃▁▁▂▃▁▂▁▁ │
                    │
 П Р О Б Л Е М Ы    │
 ⚠ 3   ✗ 12         │
 ● live             │
 pid 4821           │
 1ч 12м             │
╰───────────────────┴──────────────────── debug: скрыт · ? справка · q выход ─╯
```

Экран разделён по вопросам, на которые отвечает. **Лог справа** — что именно случилось. **Панель слева** — кто сейчас шумит, где копятся ошибки, жив ли процесс: столбик модуля красится по худшему, что у него было, так что красная полоса сразу показывает, откуда лезут ошибки. Панель прячется по `s` и сама уходит на окне уже 84 колонок — место под сообщение дороже статистики.

Уровень показывается бейджем с заливкой — `WRN` и `ERR` видно периферийным зрением, не вчитываясь. `DBG` намеренно тихий.

Подряд идущие одинаковые записи схлопываются в одну со счётчиком `×N` у правого края: одна отвалившаяся сеть больше не выдавливает с экрана всё остальное. Время показывается от последнего повтора, счётчики `⚠`/`✗` продолжают считать каждое событие.

## Зачем

Смотреть `tail -f heroku.log` глазами тяжело: в живом логе 96% строк — это `[DEBUG]` от `urllib3`, `git` и внутреннего кэша, а нужные события тонут между ними. Здесь лог разложен по колонкам, шум скрыт по умолчанию, а состояние процесса всегда перед глазами.

Лежит **вне** каталога бота намеренно: `heroku/log.py` умеет делать `reset_to_master()` и `restore_worktree()`, что может снести посторонние файлы внутри `~/Heroku`.

## Установка

Нужен [Go](https://go.dev/dl/) 1.24+ для сборки. Бот по умолчанию ищется в `~/Heroku`, каталог переопределяется переменной `HEROKU_DIR`.

```sh
git clone <этот-репозиторий> ~/heroku-console
cd ~/heroku-console
make build          # соберёт bin/hkc
./bin/hkc
```

Чтобы вызывать из любого места:

```sh
make install        # положит бинарник в ~/.local/bin/hkc
```

## Первый запуск: вход в аккаунт Telegram

Консоль умеет поднять окружение бота с нуля — склонировать репозиторий, создать `venv`, поставить зависимости, — но **войти в аккаунт Telegram вместо вас она не может**. Это разовый интерактивный шаг: Heroku при самом первом запуске спрашивает `api_id`, `api_hash`, номер телефона, код из Telegram и, если включена двухфакторка, облачный пароль. И hkc, и GUI запускают бота в фоне с выводом в файл лога, без подключённого ввода — если в этот момент бот попросит что-то ввести, ответить будет некому, и он тут же упадёт с `EOFError`. Поэтому первый вход в аккаунт нужно сделать вручную, один раз, в обычном терминале — дальше hkc и GUI управляют уже готовой сессией и это разовый шаг больше не повторяется.

### 1. Получить API_ID и API_HASH

1. Откройте [my.telegram.org/apps](https://my.telegram.org/apps) и войдите под тем номером, с которого будет работать бот.
2. Создайте приложение — название и платформа значения не имеют, вписать можно что угодно.
3. Скопируйте **App api_id** и **App api_hash**, они понадобятся на следующем шаге.

### 2. Linux Mint / Ubuntu

```sh
git clone https://github.com/coddrago/Heroku ~/Heroku
cd ~/Heroku
python3 -m venv venv          # именно venv, не .venv — под этим именем его ищут hkc и GUI
source venv/bin/activate
pip install -r requirements.txt
python3 -m heroku
```

Если `~/Heroku` уже существует — например, его сама склонировала автонастройка при первом запуске `hkc`, — просто зайдите в каталог и продолжите с `python3 -m venv venv`, `git clone` повторно не нужен.

Бот спросит `api_id`, `api_hash`, номер телефона и код из Telegram (и облачный пароль, если он у вас включён) — вводите то, что получили на шаге 1. Когда в терминале появится баннер `🪐 Heroku … started`, вход выполнен: нажмите `Ctrl+C`, чтобы остановить это разовое ручное подключение. Дальше бота запускает hkc — см. «Использование» ниже.

### 3. Windows

hkc и GUI управляют ботом только на Linux — они запускают и останавливают процесс через `bash` и читают его напрямую из `/proc`, на Windows этого просто нет. Сам бот на Python кросс-платформенный, поэтому есть два варианта:

**Вариант А — WSL (рекомендуется).** Поставьте Ubuntu через WSL (в PowerShell от администратора: `wsl --install -d Ubuntu-22.04`), а внутри неё пройдите шаг 2 целиком, как на обычном Linux. hkc и GUI, собранные и запущенные внутри той же WSL, тоже будут работать — с точки зрения Linux-подсистемы это обычный Ubuntu.

**Вариант Б — бот сам по себе, без hkc.** Тогда управлять им (запуск, остановка, перезапуск) придётся вручную, теми же командами, что и вход — консоль его не увидит и не возьмёт под присмотр:

```powershell
git clone https://github.com/coddrago/Heroku
cd Heroku
python -m venv venv
venv\Scripts\activate
pip install -r requirements.txt
python -m heroku
```

Дальше то же самое: `api_id`, `api_hash`, номер, код, при необходимости пароль. Остановка — `Ctrl+C` в этом же окне; чтобы запустить снова — та же команда `python -m heroku` из активированного `venv`, без повторного `git clone` и `pip install`.

## Использование

```sh
hkc              # проверки, затем меню выбора режима
hkc 2            # сразу нужный режим, без меню
hkc --no-check   # пропустить автонастройку и проверки (для вызова из скриптов)
hkc --no-setup   # пропустить только автонастройку, проверки оставить
hkc --version    # версия сборки
hkc --help       # краткая справка
```

Перед первым запуском консоль сама поднимает всё, чего не хватает: клонирует `~/Heroku` (или `HEROKU_DIR`), ставит `python3`, `ffmpeg` и эмулятор терминала для режима «два окна» через `apt-get`, создаёт `venv` и ставит зависимости бота из `requirements.txt`. Каждый шаг сначала проверяет, не сделано ли уже, — повторные запуски ничего не трогают. Отключается флагом `--no-setup`.

Отдельно доставляются зависимости **загруженных модулей**. `requirements.txt` бота про них не знает, а загрузчик ставит только то, что модуль объявил заголовком `# requires:`; модуль, который просто делает `import httpx`, падает при каждом старте с `ModuleNotFoundError`, и видно это лишь трейсбеком в логе. Консоль разбирает импорты всех файлов в `loaded_modules`, оставляет те, что не резолвятся в venv бота, и ставит их туда.

Импорты берутся из AST, а не поиском по тексту: `import` внутри строки или в комментарии не должен превращаться в попытку что-то поставить. Имена, которые загрузчик подменяет на лету (`telethon` и `hikkatl` разворачиваются в `herokutl`), пропускаются — ставить рядом с форком оригинал нельзя. Где имя импорта не совпадает с именем пакета, работает таблица перевода: `PIL` → `pillow`, `bs4` → `beautifulsoup4` и ещё десяток частых случаев. Пакеты ставятся по одному: имя выведено из импорта и может не найтись на PyPI, и одна промашка не должна утащить за собой остальные — что не встало, консоль назовёт поимённо.

Затем прогоняются проверки окружения — каталог бота, файл лога, venv, `python3`, `ffmpeg`, зависимости модулей, права на запись — и модульные тесты. Так причина «почему не работает» видна сразу, а не после пустого экрана. Отключаются флагом `--no-check` (заодно с автонастройкой).

Тесты запускаются с `-count=1`, то есть кэш результатов отключён: с кэшем `go test` возвращает `(cached)` за миллисекунды, и проверка сообщала бы «пройдены», ничего при этом не выполнив. Путь к исходникам вшивается в бинарник при `make build`, поэтому прогон работает и у установленной через `make install` консоли. Если репозитория на месте уже нет или Go не установлен, проверка честно помечается пропущенной.

`launch.sh` открывает консоль в новом окне терминала (ghostty, kitty или alacritty — что найдётся) — удобно повесить на ярлык рабочего стола.

### Ярлык

В репозитории лежит `Heroku Logs.desktop` с плейсхолдером вместо пути. Подставить свой и положить в меню приложений:

```sh
sed "s|/absolute/path/to/heroku-console|$PWD|" "Heroku Logs.desktop" \
    > ~/.local/share/applications/heroku-logs.desktop
```

Ярлык появится в меню приложений любого окружения (Cinnamon, MATE, Xfce и так далее), его можно закрепить в панели или доке. Чтобы получить ещё и иконку прямо на рабочем столе, та же команда, только с `~/Desktop` вместо `~/.local/share/applications`, и файлу нужны права на запуск:

```sh
sed "s|/absolute/path/to/heroku-console|$PWD|" "Heroku Logs.desktop" \
    > ~/Desktop/heroku-logs.desktop
chmod +x ~/Desktop/heroku-logs.desktop
```

Иконка на столе появляется не везде: работает в KDE Plasma и Xfce (там же может понадобиться через контекстное меню файла подтвердить «Разрешить запуск» при первом клике), в COSMIC и GNOME по умолчанию значков на рабочем столе нет вовсе — там ярлык доступен только через меню приложений.

| Режим | Что делает |
| --- | --- |
| 1 · Подключиться к боту | Показывает логи, не трогая процесс |
| 2 · Перезапустить бота | Останавливает и запускает заново |
| 3 · Два окна | Родная консоль бота в отдельном окне + лог в этом |
| 4 · Остановить бота | Просто `stop`, без просмотра логов |

В меню: `↑↓` или `jk` — выбор, `Enter` — запуск, `1`–`4` — сразу нужный режим, `q` — выход.

### Просмотр логов

| Клавиша | Действие |
| --- | --- |
| `d` | Показать или скрыть строки уровня `[DEBUG]` |
| `s` | Показать или скрыть панель статистики |
| `w` | Порог показа по кругу: всё → warning и выше → error и выше |
| `m` | Выбрать модуль из списка панели и отфильтровать по нему |
| `r` `R` | К следующему / предыдущему перезапуску бота |
| `/` | Живой поиск: ввести подстроку и Enter, пустой ввод снимает фильтр |
| `n` `N` | К следующей / предыдущей проблеме (warning и выше) |
| `?` | Справка по клавишам |
| `↑↓` `jk` | Прокрутка на строку |
| `PgUp` `PgDn` | Прокрутка на полэкрана |
| `g` `G` | В начало / в конец |
| колесо мыши | Прокрутка |
| `q` | Выйти из просмотра (бот продолжит работать) |

Выход из просмотра **не** останавливает бота — он живёт в своей сессии.

Прокрутка «прилипает» к низу: пока вы внизу, новые строки видны сразу; стоит подняться вверх почитать историю — позиция остаётся на месте, и лог не дёргает вас обратно.

Поиск ищет подстроку без учёта регистра по модулю и тексту сообщения. Активный фильтр виден в панели, в разделе «ФИЛЬТР» (`/spotify`).

Если лог перестал читаться — файл удалили, права поменялись — шапка честно говорит «⚠ лог не читается» и сколько это длится, а слежение само подхватывает файл, когда он возвращается. Ротацию (`heroku.log` крутится на 10 МБ) и обрезание файла переживает без потери строк.

Заголовок окна терминала показывает счётчики `⚠`/`✗`, а на новый warning или error подаётся звуковой сигнал — большинство эмуляторов подсвечивают вкладку или иконку в доке, так что пропустить проблему сложнее, даже если окно не в фокусе.

### GUI

Тот же бот, но нативное окно вместо терминала — тот же `HEROKU_DIR`, тот же лог, та же логика показа. Собирается и запускается отдельно (подробности — в [`gui/README.md`](gui/README.md)):

```sh
cd gui
wails build -tags webkit2_41   # на Ubuntu/Mint 24.04 доступен только webkit2gtk-4.1
./build/bin/hrk-console-gui
```

Управление вынесено в кнопки — режимов, как в меню hkc, здесь нет, окно всегда одно и то же:

| Элемент | Где | Действие |
| --- | --- | --- |
| `Start` / `Restart` / `Stop` | панель, блок «Процесс» | запуск, перезапуск, остановка бота |
| `auto-restart` | панель, блок «Процесс» | вотчдог: сам поднимает бота, если тот упал сам по себе — тот же смысл, что клавиша `a` в TUI |
| `debug` | шапка | показать/скрыть строки уровня `[DEBUG]` |
| `порог: …` | шапка | по кругу: всё → warning и выше → error и выше |
| `Очистить` | шапка | сбросить экран лога и счётчики `⚠`/`✗` (файл на диске не трогает — только что вошло, снова появится) |
| поле поиска | над логом | подстрока без учёта регистра; префикс `re:` включает регулярное выражение (`re:spotify\|tl_cache`) |

Настройки (`debug`, панель, порог, auto-restart) сохраняются в тот же `~/.config/hkc/state.json`, что и у TUI, — значения общие для обоих интерфейсов.

### Как читается строка

```
00:13:04  WRN   spotify         Token refresh took 4.2s, retrying once   ×3
└─ время ─┘ │   └─ модуль ──┘   └─ сообщение ─┘                          └ повторов
            └ бейдж уровня
```

Насыщенный цвет несёт только бейдж уровня — `DBG`, `INF`, `WRN`, `ERR`, `CRT`; заливка есть у warning и выше, debug остаётся тихим. Время и модуль приглушены, сообщение остаётся читаемым. Дата не показывается: при живом просмотре она во всех строках одна.

Перенос, который был в самом логе (трейсбек, многострочный дамп), помечается `↳`.

### Что видно при скрытом DEBUG

Всё, кроме `[DEBUG]`, плюс сообщения самого бота (модуль `root`: баннер версии, старт сессии). Периодические служебные записи вроде `Reloaded N commands` намеренно остаются в скрытой части — бот пересобирает модули каждые 30 секунд.

## Состав

| Путь | Назначение |
| --- | --- |
| `cmd/hkc` | Точка входа: разбор аргументов, автонастройка, проверки, меню, диспетчер режимов |
| `botproc` | Процесс бота: поиск в `/proc`, запуск, остановка, аптайм, версия |
| `logfeed` | Разбор строк `heroku.log`, правила видимости, слежение за файлом с переживанием ротации |
| `setup` | Автонастройка окружения бота, доустановка зависимостей загруженных модулей |
| `state` | Настройки экрана, сохранённые между запусками — общие для TUI и GUI |
| `internal/preflight` | Проверки окружения перед запуском (сами проверки, без экрана) |
| `internal/tui` | Экраны на Bubble Tea: меню, экран проверок, вьюер лога, панель статистики |
| `internal/theme` | Палитра и стили — перекрашивать TUI нужно здесь |
| `internal/termwin` | Открытие нового окна терминала для режима «два окна» |
| `gui/` | Нативное GUI-окно на Wails — отдельный Go-модуль, переиспользующий пакеты выше |
| `launch.sh`, `Heroku Logs.desktop` | Ярлык рабочего стола: открывает консоль в новом окне |
| `.github/workflows/` | CI (проверки на каждый push/PR) и Release (сборка и публикация по тегу) |

Пакеты `botproc`, `logfeed`, `setup` и `state` намеренно лежат вне `internal/` —
это чистый Go без завязки на терминал, и его переиспользует [`gui`](gui/)
(тот же бот, но нативное GUI-окно на Wails вместо TUI, отдельный Go-модуль в
этом же репозитории). Go не пускает `internal/*` за пределы дерева модуля,
поэтому TUI-специфика (`tui`, `theme`, `termwin`) остаётся под `internal/`, а
общая логика — нет.

### Как это связано

Всё завязано на одном простом факте: **сам бот ничего не знает про консоль**. Это обычный процесс `python3 -m heroku`, который пишет `heroku.log` и живёт своей жизнью — hkc и GUI лишь читают этот файл и умеют этим процессом управлять извне. Отсюда и разделение на два независимых слоя:

- **Слой процесса** (`botproc`) — «жив ли бот, как его запустить/остановить» — решается через `/proc`, без API у самого бота.
- **Слой лога** (`logfeed`) — «что в файле и что из этого показывать» — решается чтением `heroku.log`, тоже без API.

Оба интерфейса — TUI (`cmd/hkc` + `internal/tui`) и GUI (`gui/`) — это две независимые витрины поверх одних и тех же `botproc`/`logfeed`/`setup`/`state`. У каждой свой способ рисовать (Bubble Tea в терминале, HTML/CSS/JS в нативном окне), но факты о боте они получают из одного места, поэтому и ведут себя одинаково — например, настройки показа (`state`) переживают перезапуск и общие для обеих.

Путь `hkc` без аргументов: `main()` → `setup.EnsureAll` (автонастройка) → экран `internal/preflight`/`internal/tui.Preflight` (проверки) → `internal/tui.Menu` (выбор режима) → один из `modeAttach`/`modeRestart`/`modeTwoWindows`/`modeStop` в `cmd/hkc/main.go`, которые дёргают `botproc` и открывают `internal/tui.Viewer`. GUI это же самое делает в одном окне без пошагового меню: `gui/app.go` поднимает и `botproc`, и `logfeed`, и `state` сразу при старте окна.

### `cmd/hkc` — точка входа

Разбирает аргументы (`hkc`, `hkc 1..4`, `hkc console`, флаги) и решает, что показать. `--version`/`--help` отвечают раньше всего остального — до входа в Bubble Tea, чтобы работать и там, где нет терминала (скрипт, ssh, сборщик пакетов). `hkc console` — отдельный путь в обход меню: запускает бота в текущем терминале с настоящим унаследованным `stdin`/`stdout`/`stderr` (`botproc.RunForeground`, `botproc/console.go`) — то есть единственный режим, где с ботом можно взаимодействовать интерактивно; он используется и режимом «два окна» (родное окно бота), и годится для ручного первого входа в аккаунт (см. «Первый запуск» выше).

Дальше по порядку: `setup.EnsureAll` (можно пропустить `--no-setup`), экран проверок `internal/preflight` (можно пропустить вместе с настройкой через `--no-check`), меню `internal/tui.Menu`, и один из четырёх режимов — `modeAttach` (подключиться, не трогая процесс — если бот не жив, поднимает и ждёт до 2 секунд), `modeRestart` (стоп и заново), `modeTwoWindows` (родная консоль бота отдельным окном через `internal/termwin` + лог в этом), `modeStop` (просто `Stop`, без вьюера).

### `botproc` — процесс бота

Знает о боте ровно то, что можно вычитать из `/proc`, — никакого API самого бота. `PIDs()`/`PID()`/`Alive()` сканируют `/proc/*/cmdline` и ищут подстроку `"python3 -m heroku"` (важно: это подстрока, а не точное совпадение — теоретически может ложно сработать на процессе, у которого эта строка случайно встретилась в аргументах, но на практике таких коллизий не бывает). `Start()` поднимает бота в собственной сессии (`Setsid`) командой `bash -c "source venv/bin/activate && exec python3 -m heroku"`, вывод уходит в `.startup.log`, `stdin` не подключён вовсе — поэтому и нужен разовый ручной вход перед первым использованием (см. «Первый запуск» выше). `flock` на `.launch.lock` не даёт двум окнам стартовать бота одновременно. `Stop()` — сначала `SIGTERM` и до 5 секунд ожидания, затем `SIGKILL`, если не помогло. `Uptime()` вычисляется из `/proc/<pid>/stat` (поле `starttime`) и `/proc/uptime`, без внешних команд вроде `ps`. `Version()` вытаскивает номер из последнего баннера `Heroku X.X.X` в хвосте `heroku.log`.

### `logfeed` — разбор и показ лога

`parse.go`: построчный парсер (`Parser.Feed`) собирает физические строки `heroku.log` в логические записи — заголовок с `[LEVEL]` может тянуть за собой продолжение (пустое сообщение = многострочная запись впереди) или трейсбек (строка без своего заголовка приезжает как «жёсткий перенос» предыдущей записи). `shortModule` укорачивает длинные пути (`heroku.modules.spotify` → `spotify`). `SameEntry` решает, можно ли схлопнуть повтор — по уровню, модулю и тексту, но не по продолжениям (трейсбек не схлопывается: одинаковые кадры рекурсии — не повтор одного и того же события). `Visible` совмещает три независимых правила: `minLevel` (порог по важности), `showDebug` (шум скрыт по умолчанию, кроме баннера бота — `loudModules`/`loudMessages`) и `filter` (`matchFilter` — подстрока без учёта регистра, либо `re:`-регэксп, битый шаблон трактуется как «не совпало», а не паника).

`tail.go`: `TailLines` — кольцевой буфер для стартовой истории (без квадратичной пересборки на больших файлах). `Follower` — собственная замена `tail -F`: опрашивает файл каждые 250мс, переживает ротацию (`heroku.log` крутится на 10 МБ) и обрезание на месте, не отдаёт недописанную половину строки (копит в `partial`, пока не встретит перевод строки — бот пишет не атомарно), и в отличие от внешнего `tail` умеет сказать *почему* не читается (`Alive()` возвращает причину и с какого момента), а не просто молча замолчать.

### `setup` — автонастройка окружения

`setup.go`: `EnsureAll` идёт по цепочке (клонировать `~/Heroku`, если нет → поставить `python3`/`python3-venv` → создать `venv` и поставить `requirements.txt` → эмулятор терминала для режима «два окна» → `ffmpeg`), каждый шаг сам проверяет, не сделано ли уже, и заставка на экране появляется только если реально есть что делать. Ставит через `sudo apt-get install -y` — то есть рассчитан на Debian/Ubuntu-семейство (Mint в их числе); на другом дистрибутиве просто попросит поставить руками.

`deps.go` — отдельная, более тонкая задача: зависимости **загруженных модулей бота**, про которые `requirements.txt` ничего не знает. Питоновский скрипт (`depScanScript`), встроенный прямо в Go-код как строка, запускается через `venv/bin/python` бота и через `ast.parse` (не regex по тексту — закомментированный `import` не должен считаться зависимостью) собирает все импорты `loaded_modules/*.py` и заголовки `# requires:`, отсеивает то, что уже резолвится, отсеивает имена, которые загрузчик Heroku подменяет на лету (`telethon`/`hikkatl` → `herokutl`), переводит расхождения импорт↔пакет по таблице (`PIL`→`pillow` и ещё десяток) и ставит каждый пакет отдельным `pip install` — одна не найденная на PyPI промашка не должна ронять остальные. Пакеты, которые уже не встали, попадают в `.hkc-failed-deps.json` в каталоге бота и не трогаются повторно сутки — угаданное по импорту имя может быть в принципе неверным, и без паузы каждый запуск консоли заново пытался бы поставить то, что никогда не встанет.

### `internal/preflight` — проверки окружения

Список из восьми проверок (`All`): каталог бота, файл лога, `venv`, `python3`, `ffmpeg`, зависимости модулей, права на запись (`.launch.lock`), модульные тесты. Тесты гоняются `go test -count=1 -json ./...` с таймаутом 2 минуты по пути к исходникам, вшитому в бинарник при сборке (`-X ...preflight.repoRoot=`) — без этого у консоли, установленной в `~/.local/bin`, тесты не запускались бы никогда, потому что исходников рядом с бинарником уже нет. Каждая проверка возвращает пояснение даже при успехе («venv найден») — молчаливая галочка отвечает на меньше вопросов, чем текст рядом с ней.

### `internal/tui` — экраны

Всё на [Bubble Tea](https://github.com/charmbracelet/bubbletea)/[Lip Gloss](https://github.com/charmbracelet/lipgloss): `menu.go` (карточка выбора режима с живым PID/аптаймом бота), `preflight.go` (анимированная обёртка вокруг `internal/preflight` — спиннер, прогресс-бар, при провале держит экран до нажатия клавиши), `viewer.go` (главный экран — живой лог, вотчдог, поиск, вся логика показа), `sidebar.go` (панель статистики: модули с градиентными барами, sparkline активности, счётчики проблем, блок процесса), `render.go` (раскладка колонок, рамка окна с градиентом, оверлеи справки и выбора модуля), `screen.go` (накопитель отрисованных блоков — держит схлопывание повторов, позиции проблемных записей для `n`/`N`, чётность зебры).

Вьюер держит в памяти кольцевой буфер сырых строк (`ring`, 5000 штук) — не только то, что видно на экране, а достаточно, чтобы при смене фильтра или порога показа пересобрать экран из истории, а не только из новых строк. Вотчдог (клавиша `a`) выключен по умолчанию: режим «Подключиться, не трогая процесс» по контракту не должен трогать процесс без явного согласия. Настройки показа (`state`) загружаются при старте вьюера и сохраняются при выходе.

### `internal/theme` — визуальный язык

Один источник цвета и стилей на весь TUI. Палитра в духе btop/htop — насыщенная, без рамок вокруг каждого виджета (разделение цветом и отступом, не линиями); маркер уровня лога — единственное, что несёт по-настоящему яркий цвет, всё остальное приглушено, чтобы взгляд цеплялся именно за уровень записи. `Gradient()` красит линии рамки перетеканием акцент→фон (через Lab-пространство, [go-colorful](https://github.com/lucasb-eyer/go-colorful)) вместо ровной заливки. `MeterBar()` — фирменный элемент btop/htop: столбик градиентом зелёный→жёлтый→красный по своей заполненной доле, температура столбика видна раньше, чем его длина. `Sparkline()` — восемь уровней блочных символов для графика активности.

### `internal/termwin` — окно терминала

`Open()` для режима «два окна»: перебирает эмуляторы по порядку — сначала три с гибкой раскраской (`ghostty`, `kitty`, `alacritty`), затем штатные терминалы окружений Mint (`gnome-terminal`/Cinnamon, `mate-terminal`/MATE, `xfce4-terminal`/Xfce — из них только `xfce4-terminal` умеет красить фон), последним — `x-terminal-emulator` (alternatives-symlink на дефолтный терминал системы). Возвращает `false`, если вообще ничего не нашлось — тогда `cmd/hkc` откатывается на запуск в текущем терминале.

### `state` — персистентность настроек

Четыре поля (`ShowDebug`, `ShowSidebar`, `MinLevel`, `Watchdog`) в JSON по стандартному пути (`os.UserConfigDir()/hkc/state.json`, обычно `~/.config/hkc/state.json`). Любая ошибка чтения (файла нет, битый JSON, недоступен конфиг-каталог) тихо откатывается на `Default` — настройки экрана не стоят того, чтобы ронять запуск сообщением об ошибке. Файл общий у TUI и GUI: переключили `debug` в одном интерфейсе — при следующем открытии другого оно уже включено.

### `gui/` — нативное окно (Wails)

Отдельный Go-модуль (`hrk-console-gui`, свой `go.mod`) внутри этого же репозитория, подключающий корневые пакеты через `replace heroku-console => ../`. `app.go` — весь бэкенд: `App` держит `botproc.Manager`, парсер `logfeed`, кольцевой буфер и видимые записи под мьютексом; при старте окна (`startup`) загружает `state`, поднимает историю из `heroku.log`, запускает две фоновые горутины — `followLog` (живой хвост через `logfeed.Follower`, incremental-схлопывание против последней показанной записи) и `statusLoop` (раз в секунду шлёт статус во фронтенд и проверяет вотчдог). Методы, вызываемые из JS (`Bootstrap`, `SetFilter`, `SetShowDebug`, `CycleMinLevel`, `SetWatchdog`, `StartBot`/`StopBot`/`RestartBot`, `ClearLog`), — обычные Go-методы, Wails сам генерирует JS-обвязку (`frontend/wailsjs`, не хранится в репозитории, собирается заново).

Вотчдог в GUI — зеркало TUI-вотчдога с той же логикой кулдауна, но с важным отличием: GUI-окно тикает **всегда**, даже когда бот вообще не запущен (TUI входит в вьюер только когда бот уже жив), поэтому вотчдог здесь дополнительно «вооружается» лишь после того, как хоть раз застал бота реально живым (`everAlive`) — иначе на свежеоткрытом окне с сохранённым `auto-restart: включён` он путал бы «бот ещё не поднят» с «бот упал» (починено в `v1.6.1`, см. `CHANGELOG.md`).

`frontend/src/main.js` — фронтенд без фреймворка (vanilla JS): DOM строится из шаблонной строки один раз, дальше только точечные обновления. Приём новых строк батчится через `requestAnimationFrame` кусками по 300 записей — построчное чтение `scrollHeight`/запись `scrollTop` на каждую строку давало forced layout reflow и многосекундное подвисание на всплеске из сотен строк. `style.css` — тёмная тема на CSS custom properties, цвета module-барам назначаются хешем имени в восемь `--mod-N` (та же идея, что `moduleColor` в TUI). Собирается `wails build -tags webkit2_41` — на Ubuntu/Mint 24.04 в репозиториях остался только `webkit2gtk-4.1`, тег переключает Wails на него.

### `launch.sh` и `Heroku Logs.desktop`

`launch.sh` — то же самое, что `internal/termwin.Open`, но отдельным bash-скриптом: он нужен как раз потому, что запускается *до* всего Go-кода, чтобы вообще открыть терминал для ярлыка рабочего стола (список эмуляторов продублирован, а не переиспользован — на этом шаге ещё нет собранного `hkc`, который мог бы это сделать сам). `Heroku Logs.desktop` — шаблон XDG-ярлыка с плейсхолдером вместо абсолютного пути, заполняется командой `sed` из раздела «Ярлык» выше.

### CI и релизы

`.github/workflows/ci.yml` — на каждый push в `main` и на каждый PR: `gofmt -l` (отдельным шагом, а не на глаз в ревью), `go vet`, `go test -count=1 -race` (без кэша и с детектором гонок), `make build`. `.github/workflows/release.yml` — по тегу `v*`: те же проверки, сборка, архив `hkc-<тег>-linux-amd64.tar.gz`, и тело релиза — не написанное руками, а вырезанное `awk`-ом из `CHANGELOG.md` по секции `## [версия]` (один источник правды: то, что видно на странице релиза на GitHub, и то, что лежит в репозитории, не могут разойтись), публикуется через `softprops/action-gh-release`.

### `Makefile`

`VERSION` берётся из `git describe --tags --dirty` — сборка из грязного рабочего дерева получает суффикс, и «у меня другая версия» видно сразу, без сверки хешей. `CGO_ENABLED=0` — проект не использует cgo вообще (`/proc` и `syscall` читаются напрямую), но `go build` включает его сам, если в `PATH` нашёлся `gcc`, и без заголовков libc сборка падает на компиляции `runtime/cgo`, хотя самому проекту он не нужен. `LDFLAGS` вшивает и версию, и путь к исходникам (`preflight.repoRoot`) — второе нужно, чтобы модульные тесты в `internal/preflight` находили `go.mod` и после `make install`.
