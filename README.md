Консоль для Telegram-юзербота [Heroku](https://github.com/coddrago/Heroku): запуск, остановка и живой просмотр логов — из терминала (TUI) или из нативного окна (GUI).

## Зачем

Смотреть `tail -f heroku.log` глазами тяжело: в живом логе 96% строк — это `[DEBUG]` от `urllib3`, `git` и внутреннего кэша, а нужные события тонут между ними. Здесь лог разложен по колонкам, шум скрыт по умолчанию, а состояние процесса всегда перед глазами.

Лежит **вне** каталога бота намеренно: `heroku/log.py` умеет делать `reset_to_master()` и `restore_worktree()`, что может снести посторонние файлы внутри `~/Heroku`.

## Установка

Бот по умолчанию ищется в `~/Heroku`, каталог переопределяется переменной `HEROKU_DIR`.

### Поставить Go

Нужен свежий [Go](https://go.dev) — репозиторий пакетов Ubuntu/Mint обычно отстаёт на пару версий, поэтому надёжнее взять официальный архив:

```sh
curl -LO "https://go.dev/dl/$(curl -s https://go.dev/VERSION?m=text | head -1).linux-amd64.tar.gz"
sudo rm -rf /usr/local/go && sudo tar -C /usr/local -xzf go*.linux-amd64.tar.gz
echo 'export PATH=$PATH:/usr/local/go/bin' >> ~/.bashrc
source ~/.bashrc
go version
```

<details>
<summary>Другие способы</summary>

**Snap** (проще, но версия может отставать от официальной на релиз-другой):

```sh
sudo snap install go --classic
```

**apt** — версия в репозиториях Ubuntu 24.04/Mint 22, как правило, старше, чем требует `go.mod`; если `go build` пожалуется на версию, используйте способ выше:

```sh
sudo apt update && sudo apt install golang-go
```

Если версия установленного Go всё же старше нужной, а сеть есть — сам `go build`/`make build` молча докачает нужный тулчейн (`GOTOOLCHAIN=auto` включён по умолчанию), отдельно ничего обновлять не придётся.
</details>

### Собрать консоль

```sh
git clone <этот-репозиторий> ~/heroku-console
cd ~/heroku-console
make build          # соберёт bin/hkc
./bin/hkc
```

Чтобы вызывать из любого места:

```sh
make install        # положит бинарник в ~/.local/bin/hkc
```

## Первый запуск и вход в аккаунт

Консоль умеет поднять окружение бота с нуля — склонировать репозиторий, создать `venv`, поставить зависимости, — но **войти в аккаунт Telegram вместо вас она не может**. Это разовый интерактивный шаг: Heroku при самом первом запуске спрашивает `api_id`, `api_hash`, номер телефона, код из Telegram и, если включена двухфакторка, облачный пароль. И hkc, и GUI запускают бота в фоне с выводом в файл лога, без подключённого ввода — если в этот момент бот попросит что-то ввести, ответить будет некому, и он тут же упадёт с `EOFError`.

Поэтому первый вход нужно сделать вручную, один раз, в обычном терминале — дальше hkc и GUI управляют уже готовой сессией.

**1. Получить API_ID и API_HASH.** Откройте [my.telegram.org/apps](https://my.telegram.org/apps), войдите под тем номером, с которого будет работать бот, создайте приложение (название и платформа значения не имеют) и скопируйте **App api_id** и **App api_hash**.

**2. Linux Mint / Ubuntu:**

```sh
git clone https://github.com/coddrago/Heroku ~/Heroku
cd ~/Heroku
python3 -m venv venv          # именно venv, не .venv — под этим именем его ищут hkc и GUI
source venv/bin/activate
pip install -r requirements.txt
python3 -m heroku
```

Если `~/Heroku` уже существует (например, его сама склонировала автонастройка при первом запуске `hkc`) — просто зайдите в каталог и продолжите с `python3 -m venv venv`, `git clone` повторно не нужен.

Бот спросит `api_id`, `api_hash`, номер телефона и код из Telegram (и облачный пароль, если он у вас включён). Когда появится баннер `🪐 Heroku … started` — вход выполнен, нажмите `Ctrl+C`. Дальше бота запускает hkc — см. [«Использование»](#использование).

<details>
<summary><b>3. Windows</b></summary>

hkc и GUI управляют ботом только на Linux — они запускают и останавливают процесс через `bash` и читают его напрямую из `/proc`, на Windows этого просто нет. Сам бот на Python кросс-платформенный, поэтому есть два варианта:

**Вариант А — WSL (рекомендуется).** Поставьте Ubuntu через WSL (в PowerShell от администратора: `wsl --install -d Ubuntu-22.04`), а внутри неё пройдите шаг 2 целиком, как на обычном Linux. hkc и GUI, собранные и запущенные внутри той же WSL, тоже будут работать — с точки зрения Linux-подсистемы это обычный Ubuntu.

**Вариант Б — бот сам по себе, без hkc.** Управлять им (запуск, остановка, перезапуск) придётся вручную теми же командами, что и вход — консоль его не увидит:

```powershell
git clone https://github.com/coddrago/Heroku
cd Heroku
python -m venv venv
venv\Scripts\activate
pip install -r requirements.txt
python -m heroku
```

Дальше то же самое: `api_id`, `api_hash`, номер, код, при необходимости пароль. Остановка — `Ctrl+C`; чтобы запустить снова — та же команда `python -m heroku` из активированного `venv`, без повторного `git clone` и `pip install`.
</details>

## Использование

```sh
hkc              # проверки, затем меню выбора режима
hkc 2            # сразу нужный режим, без меню
hkc console      # родная консоль бота в текущем терминале (интерактивно)
hkc --no-check   # пропустить автонастройку и проверки (для вызова из скриптов)
hkc --no-setup   # пропустить только автонастройку, проверки оставить
hkc --version    # версия сборки
hkc --help       # краткая справка
```

Перед первым запуском консоль сама доустанавливает недостающее (клонирует бота, ставит `python3`/`ffmpeg`/`venv`/зависимости) и прогоняет проверки окружения — как именно, подробно расписано в [«Устройство проекта»](#устройство-проекта). Отключается флагами `--no-setup`/`--no-check`.

### Режимы

| Режим | Что делает |
| --- | --- |
| 1 · Подключиться к боту | Показывает логи, не трогая процесс |
| 2 · Перезапустить бота | Останавливает и запускает заново |
| 3 · Два окна | Родная консоль бота в отдельном окне + лог в этом |
| 4 · Остановить бота | Просто `stop`, без просмотра логов |

В меню: `↑↓`/`jk` — выбор, `Enter` — запуск, `1`–`4` — сразу нужный режим, `q` — выход.

### Просмотр логов (TUI)

| Клавиша | Действие |
| --- | --- |
| `d` | Показать/скрыть строки уровня `DEBUG` |
| `s` | Показать/скрыть панель статистики |
| `w` | Порог показа по кругу: всё → warning+ → error+ |
| `m` | Выбрать модуль из панели и отфильтровать по нему |
| `a` | Автоперезапуск бота при падении: вкл/выкл |
| `/` | Живой поиск: подстрока или `re:шаблон`, пустой ввод снимает фильтр |
| `n` `N` | К следующей / предыдущей проблеме (warning и выше) |
| `r` `R` | К следующему / предыдущему перезапуску бота |
| `?` | Справка по клавишам |
| `↑↓` `jk` · `PgUp/PgDn` · `g`/`G` · колесо мыши | Прокрутка |
| `q` | Выйти из просмотра (бот продолжит работать) |

<details>
<summary>Детали поведения — прилипание прокрутки, поиск, обрыв лога</summary>

Прокрутка «прилипает» к низу: пока вы внизу, новые строки видны сразу; поднялись выше почитать историю — позиция остаётся на месте, лог не дёргает обратно.

Поиск ищет подстроку без учёта регистра по модулю и тексту сообщения; префикс `re:` включает регулярное выражение. Активный фильтр виден в панели, в разделе «ФИЛЬТР».

Если лог перестал читаться (файл удалили, права поменялись) — шапка честно говорит «⚠ лог не читается» и сколько это длится, слежение само подхватывает файл, когда он возвращается. Ротацию (`heroku.log` крутится на 10 МБ) и обрезание файла переживает без потери строк.

Заголовок окна терминала показывает счётчики `⚠`/`✗`, на новый warning или error подаётся звуковой сигнал — большинство эмуляторов подсвечивают вкладку или иконку в доке.

Строка читается так:

```
00:13:04  WRN   spotify         Token refresh took 4.2s, retrying once   ×3
└─ время ─┘ │   └─ модуль ──┘   └─ сообщение ─┘                          └ повторов
            └ бейдж уровня
```

Насыщенный цвет несёт только бейдж уровня; при скрытом `DEBUG` видно всё, кроме него, плюс сообщения самого бота (баннер версии, старт сессии) — периодические служебные записи вроде `Reloaded N commands` остаются скрытыми.
</details>

### GUI

Тот же бот, но нативное окно вместо терминала — тот же `HEROKU_DIR`, тот же лог, та же логика показа (подробности сборки — в [`gui/README.md`](gui/README.md)):

```sh
cd gui
wails build -tags webkit2_41   # на Ubuntu/Mint 24.04 доступен только webkit2gtk-4.1
./build/bin/hrk-console-gui
```

Режимов, как в меню hkc, здесь нет — управление вынесено в кнопки:

| Элемент | Где | Действие |
| --- | --- | --- |
| `Start` / `Restart` / `Stop` | панель, блок «Процесс» | запуск, перезапуск, остановка бота |
| `auto-restart` | панель, блок «Процесс» | вотчдог — тот же смысл, что клавиша `a` в TUI |
| `debug` | шапка | показать/скрыть строки уровня `DEBUG` |
| `порог: …` | шапка | по кругу: всё → warning+ → error+ |
| `Очистить` | шапка | сбросить экран лога и счётчики (файл на диске не трогает) |
| поле поиска | над логом | подстрока или `re:шаблон`, как в TUI |

Настройки (`debug`, панель, порог, auto-restart) сохраняются в общий с TUI `~/.config/hkc/state.json`.

### Ярлык на рабочем столе

`launch.sh` открывает консоль в новом окне терминала — удобно повесить на ярлык. В репозитории лежит `Heroku Logs.desktop` с плейсхолдером вместо пути:

```sh
sed "s|/absolute/path/to/heroku-console|$PWD|" "Heroku Logs.desktop" \
    > ~/.local/share/applications/heroku-logs.desktop
```

Ярлык появится в меню приложений любого окружения (Cinnamon, MATE, Xfce и так далее). Чтобы получить иконку прямо на рабочем столе — та же команда, но с `~/Desktop`, и файлу нужны права на запуск:

```sh
sed "s|/absolute/path/to/heroku-console|$PWD|" "Heroku Logs.desktop" \
    > ~/Desktop/heroku-logs.desktop
chmod +x ~/Desktop/heroku-logs.desktop
```

<details>
<summary>Где иконка на столе появляется, а где нет</summary>

Работает в KDE Plasma и Xfce (там может понадобиться через контекстное меню файла подтвердить «Разрешить запуск» при первом клике). В COSMIC и GNOME значков на рабочем столе по умолчанию нет вовсе — там ярлык доступен только через меню приложений.
</details>

## Устройство проекта

Всё завязано на одном факте: **сам бот ничего не знает про консоль**. Это обычный процесс `python3 -m heroku`, который пишет `heroku.log` и живёт своей жизнью — hkc и GUI лишь читают этот файл и умеют управлять процессом извне, без какого-либо API у самого бота.

TUI (`cmd/hkc` + `internal/tui`) и GUI (`gui/`) — две независимые витрины поверх одних и тех же пакетов ниже. У каждой свой способ рисовать, но факты о боте они получают из одного места, поэтому и ведут себя одинаково — например, настройки показа (`state`) общие для обеих.

| Путь | Назначение |
| --- | --- |
| `cmd/hkc` | Точка входа: разбор аргументов, автонастройка, проверки, меню, диспетчер режимов |
| `botproc` | Процесс бота: поиск в `/proc`, запуск, остановка, аптайм, версия |
| `logfeed` | Разбор строк `heroku.log`, правила видимости, слежение за файлом с переживанием ротации |
| `setup` | Автонастройка окружения бота, доустановка зависимостей загруженных модулей |
| `state` | Настройки экрана, сохранённые между запусками — общие для TUI и GUI |
| `internal/preflight` | Проверки окружения перед запуском (сами проверки, без экрана) |
| `internal/tui` | Экраны на Bubble Tea: меню, экран проверок, вьюер лога, панель статистики |
| `internal/theme` | Палитра и стили — перекрашивать TUI нужно здесь |
| `internal/termwin` | Открытие нового окна терминала для режима «два окна» |
| `gui/` | Нативное GUI-окно на Wails — отдельный Go-модуль, переиспользующий пакеты выше |
| `launch.sh`, `Heroku Logs.desktop` | Ярлык рабочего стола |
| `.github/workflows/` | CI (проверки на каждый push/PR) и Release (сборка и публикация по тегу) |

Пакеты `botproc`, `logfeed`, `setup` и `state` намеренно лежат вне `internal/` — это чистый Go без завязки на терминал, и его переиспользует `gui`. Go не пускает `internal/*` за пределы дерева модуля, поэтому TUI-специфика (`tui`, `theme`, `termwin`) остаётся под `internal/`, а общая логика — нет.

Путь `hkc` без аргументов: `main()` → `setup.EnsureAll` → экран `internal/tui.Preflight` → `internal/tui.Menu` → один из `modeAttach`/`modeRestart`/`modeTwoWindows`/`modeStop`, которые дёргают `botproc` и открывают `internal/tui.Viewer`. GUI делает то же самое в одном окне без пошагового меню: `gui/app.go` поднимает `botproc`, `logfeed` и `state` сразу при старте окна.

Ниже — как устроена каждая часть по отдельности (разворачивается по клику):

<details>
<summary><code>cmd/hkc</code> — точка входа</summary>

Разбирает аргументы (`hkc`, `hkc 1..4`, `hkc console`, флаги) и решает, что показать. `--version`/`--help` отвечают раньше всего остального — до входа в Bubble Tea, чтобы работать и там, где нет терминала (скрипт, ssh, сборщик пакетов).

`hkc console` — отдельный путь в обход меню: запускает бота в текущем терминале с настоящим унаследованным `stdin`/`stdout`/`stderr` (`botproc.RunForeground`) — единственный режим, где с ботом можно взаимодействовать интерактивно. Его использует режим «два окна» (родное окно бота), и он же годится для ручного первого входа в аккаунт (см. [«Первый запуск»](#первый-запуск-и-вход-в-аккаунт)).

Дальше по порядку: `setup.EnsureAll` (пропускается `--no-setup`) → экран проверок `internal/preflight` (пропускается вместе с настройкой через `--no-check`) → меню `internal/tui.Menu` → один из четырёх режимов: `modeAttach` (подключиться, не трогая процесс — если бот не жив, поднимает и ждёт до 2 секунд), `modeRestart` (стоп и заново), `modeTwoWindows` (родная консоль бота отдельным окном через `internal/termwin` + лог в этом), `modeStop` (просто `Stop`, без вьюера).
</details>

<details>
<summary><code>botproc</code> — процесс бота</summary>

Знает о боте ровно то, что можно вычитать из `/proc` — никакого API у самого бота. `PIDs()`/`PID()`/`Alive()` сканируют `/proc/*/cmdline` и ищут подстроку `"python3 -m heroku"` (это подстрока, а не точное совпадение — теоретически может ложно сработать на процессе, у которого эта строка случайно встретилась в аргументах, но на практике таких коллизий не бывает).

`Start()` поднимает бота в собственной сессии (`Setsid`) командой `bash -c "source venv/bin/activate && exec python3 -m heroku"`, вывод уходит в `.startup.log`, `stdin` не подключён вовсе — поэтому и нужен разовый ручной вход перед первым использованием. `flock` на `.launch.lock` не даёт двум окнам стартовать бота одновременно.

`Stop()` — сначала `SIGTERM` и до 5 секунд ожидания, затем `SIGKILL`, если не помогло. `Uptime()` вычисляется из `/proc/<pid>/stat` (поле `starttime`) и `/proc/uptime`, без внешних команд вроде `ps`. `Version()` вытаскивает номер из последнего баннера `Heroku X.X.X` в хвосте `heroku.log`.
</details>

<details>
<summary><code>logfeed</code> — разбор и показ лога</summary>

`parse.go`: построчный парсер (`Parser.Feed`) собирает физические строки `heroku.log` в логические записи — заголовок с `[LEVEL]` может тянуть за собой продолжение (пустое сообщение = многострочная запись впереди) или трейсбек (строка без своего заголовка приезжает как «жёсткий перенос» предыдущей записи). `SameEntry` решает, можно ли схлопнуть повтор — по уровню, модулю и тексту, но не по продолжениям (трейсбек не схлопывается: одинаковые кадры рекурсии — не повтор одного и того же события). `Visible` совмещает три независимых правила: `minLevel` (порог по важности), `showDebug` (шум скрыт по умолчанию, кроме баннера бота) и `filter` (`matchFilter` — подстрока без учёта регистра либо `re:`-регэксп; битый шаблон трактуется как «не совпало», а не паника).

`tail.go`: `TailLines` — кольцевой буфер для стартовой истории. `Follower` — собственная замена `tail -F`: опрашивает файл каждые 250мс, переживает ротацию (`heroku.log` крутится на 10 МБ) и обрезание на месте, не отдаёт недописанную половину строки (бот пишет не атомарно), и умеет сказать *почему* не читается, а не просто молча замолчать.
</details>

<details>
<summary><code>setup</code> — автонастройка окружения</summary>

`setup.go`: `EnsureAll` идёт по цепочке (клонировать `~/Heroku`, если нет → `python3`/`python3-venv` → `venv` + `requirements.txt` → эмулятор терминала для «два окна» → `ffmpeg`), каждый шаг сам проверяет, не сделано ли уже, заставка появляется только если реально есть что делать. Ставит через `sudo apt-get install -y` — рассчитан на Debian/Ubuntu-семейство (Mint в их числе).

`deps.go` — отдельная задача: зависимости **загруженных модулей бота**, про которые `requirements.txt` ничего не знает. Питоновский скрипт, встроенный в Go-код строкой, запускается через `venv/bin/python` бота и через `ast.parse` (не regex — закомментированный `import` не должен считаться зависимостью) собирает импорты `loaded_modules/*.py` и заголовки `# requires:`, отсеивает то, что уже резолвится и что загрузчик Heroku подменяет на лету (`telethon`/`hikkatl` → `herokutl`), переводит расхождения импорт↔пакет по таблице (`PIL`→`pillow` и ещё десяток) и ставит каждый пакет отдельным `pip install` — одна промашка не должна ронять остальные. Пакеты, которые не встали, попадают в `.hkc-failed-deps.json` и не трогаются повторно сутки.
</details>

<details>
<summary><code>internal/preflight</code> — проверки окружения</summary>

Восемь проверок: каталог бота, файл лога, `venv`, `python3`, `ffmpeg`, зависимости модулей, права на запись, модульные тесты. Тесты гоняются `go test -count=1 -json ./...` по пути к исходникам, вшитому в бинарник при сборке (`-X ...preflight.repoRoot=`) — без этого у консоли, установленной в `~/.local/bin`, тесты не запускались бы никогда. Каждая проверка возвращает пояснение даже при успехе.
</details>

<details>
<summary><code>internal/tui</code> — экраны</summary>

Всё на [Bubble Tea](https://github.com/charmbracelet/bubbletea)/[Lip Gloss](https://github.com/charmbracelet/lipgloss): `menu.go` (выбор режима с живым PID/аптаймом бота), `preflight.go` (анимированная обёртка вокруг `internal/preflight`), `viewer.go` (главный экран — живой лог, вотчдог, поиск), `sidebar.go` (панель: модули с градиентными барами, sparkline активности, счётчики проблем), `render.go` (раскладка колонок, рамка с градиентом, оверлеи), `screen.go` (накопитель отрисованных блоков — схлопывание повторов, позиции проблем для `n`/`N`, зебра).

Вьюер держит кольцевой буфер сырых строк (5000 штук) — достаточно, чтобы при смене фильтра или порога пересобрать экран из истории. Вотчдог (`a`) выключен по умолчанию: режим «Подключиться, не трогая процесс» по контракту не должен трогать процесс без явного согласия.
</details>

<details>
<summary><code>internal/theme</code> — визуальный язык</summary>

Один источник цвета и стилей на весь TUI. Палитра в духе btop/htop — насыщенная, без рамок вокруг каждого виджета. `Gradient()` красит линии рамки перетеканием акцент→фон через Lab-пространство ([go-colorful](https://github.com/lucasb-eyer/go-colorful)). `MeterBar()` — столбик градиентом зелёный→жёлтый→красный по заполненной доле. `Sparkline()` — восемь уровней блочных символов для графика активности.
</details>

<details>
<summary><code>internal/termwin</code> — окно терминала</summary>

`Open()` для режима «два окна»: перебирает эмуляторы по порядку — три с гибкой раскраской (`ghostty`, `kitty`, `alacritty`), затем штатные терминалы окружений Mint (`gnome-terminal`/Cinnamon, `mate-terminal`/MATE, `xfce4-terminal`/Xfce), последним — `x-terminal-emulator`. Возвращает `false`, если ничего не нашлось — тогда `cmd/hkc` откатывается на запуск в текущем терминале.
</details>

<details>
<summary><code>state</code> — персистентность настроек</summary>

Четыре поля (`ShowDebug`, `ShowSidebar`, `MinLevel`, `Watchdog`) в JSON по стандартному пути (обычно `~/.config/hkc/state.json`). Любая ошибка чтения тихо откатывается на значения по умолчанию. Файл общий у TUI и GUI: переключили `debug` в одном — при следующем открытии другого оно уже включено.
</details>

<details>
<summary><code>gui/</code> — нативное окно (Wails)</summary>

Отдельный Go-модуль (`hrk-console-gui`, свой `go.mod`) внутри этого же репозитория, подключающий корневые пакеты через `replace heroku-console => ../`. `app.go` — весь бэкенд: `App` держит `botproc.Manager`, парсер `logfeed`, буфер записей под мьютексом; при старте окна загружает `state`, поднимает историю из `heroku.log`, запускает две горутины — `followLog` (живой хвост) и `statusLoop` (раз в секунду шлёт статус и проверяет вотчдог). Методы, вызываемые из JS (`Bootstrap`, `SetFilter`, `StartBot`/`StopBot`/`RestartBot`, `ClearLog` и другие), — обычные Go-методы, Wails сам генерирует JS-обвязку.

Вотчдог в GUI — зеркало TUI-вотчдога, но с важным отличием: GUI-окно тикает **всегда**, даже когда бот не запущен (TUI входит в вьюер только когда бот уже жив), поэтому вотчдог здесь дополнительно «вооружается» лишь после того, как хоть раз застал бота реально живым — иначе на свежеоткрытом окне с сохранённым `auto-restart: включён` он путал бы «бот ещё не поднят» с «бот упал» (починено в `v1.6.1`, см. `CHANGELOG.md`).

`frontend/src/main.js` — vanilla JS без фреймворка: DOM строится один раз из шаблонной строки, дальше только точечные обновления. Приём новых строк батчится через `requestAnimationFrame` кусками по 300 записей — построчное чтение/запись `scrollTop` на каждую строку давало forced layout reflow и подвисание на всплеске из сотен строк. Собирается `wails build -tags webkit2_41` — на Ubuntu/Mint 24.04 в репозиториях остался только `webkit2gtk-4.1`.
</details>

<details>
<summary><code>launch.sh</code> и <code>Heroku Logs.desktop</code></summary>

`launch.sh` — то же самое, что `internal/termwin.Open`, но отдельным bash-скриптом: запускается *до* всего Go-кода, чтобы вообще открыть терминал для ярлыка рабочего стола. `Heroku Logs.desktop` — шаблон XDG-ярлыка с плейсхолдером вместо абсолютного пути, заполняется командой `sed` из раздела [«Ярлык»](#ярлык-на-рабочем-столе).
</details>

<details>
<summary>CI и релизы</summary>

`.github/workflows/ci.yml` — на каждый push в `main` и каждый PR: `gofmt -l`, `go vet`, `go test -count=1 -race`, `make build`.

`.github/workflows/release.yml` — по тегу `v*`: те же проверки, сборка, архив `hkc-<тег>-linux-amd64.tar.gz`, и тело релиза — вырезанное `awk`-ом из `CHANGELOG.md` по секции `## [версия]` (то, что видно на странице релиза, и то, что лежит в репозитории, не могут разойтись), публикуется через `softprops/action-gh-release`.
</details>

<details>
<summary><code>Makefile</code></summary>

`VERSION` берётся из `git describe --tags --dirty` — сборка из грязного рабочего дерева получает суффикс. `CGO_ENABLED=0` — проект не использует cgo вообще (`/proc` и `syscall` читаются напрямую), но `go build` включает его сам, если в `PATH` нашёлся `gcc`, и без заголовков libc сборка падает на компиляции `runtime/cgo`. `LDFLAGS` вшивает и версию, и путь к исходникам (`preflight.repoRoot`) — нужен, чтобы модульные тесты находили `go.mod` и после `make install`.
</details>
