# Веб-интерфейс

`hkc-web` — единственный интерфейс hrk-console 2.0. Сервер запускается рядом
с ботом на Linux/WSL, а панель открывается обычным браузером с любой ОС.
Кнопки управляют настоящим процессом Heroku, а лог приходит в браузер живым
SSE-потоком.

Для запуска Heroku используется Python из `venv/bin/python3` или
`.venv/bin/python3` внутри `HEROKU_DIR`.

## Сборка и запуск

```sh
make build
HKC_ADMIN_TOKEN='замените-на-длинный-случайный-секрет' \
HEROKU_DIR=/mnt/c/Users/ayanami/Heroku \
./bin/hkc-web
```

По умолчанию сервер слушает только `127.0.0.1:8080`. Из Windows при обычной
настройке WSL страница доступна по адресу <http://localhost:8080>.

Дополнительные переменные:

| Переменная | По умолчанию | Назначение |
| --- | --- | --- |
| `HKC_WEB_ADDR` | `127.0.0.1:8080` | адрес веб-сервера |
| `HKC_ADMIN_TOKEN` | случайный при каждом старте | секрет API создания инвайтов |
| `HKC_AUTH_FILE` | `~/.config/hkc/web-auth.json` | база пользователей и инвайтов |
| `HEROKU_DIR` | `~/Heroku` | каталог бота |
| `HKC_WEBHOOK_URL` | не задан | HTTPS endpoint для JSON уведомлений о запуске/остановке бота |
| `HKC_PUBLIC_STATUS` | не задан | значение `1` открывает `/api/public/status` и страницу `/status.html` без входа |

Если `HKC_ADMIN_TOKEN` не задан, сервер печатает временный токен при старте.
Для постоянной установки его следует задать явно и хранить как пароль.

## Инвайты и регистрация

Инвайт создаёт только администратор. Пример для инвайта на 24 часа:

```sh
curl -X POST http://localhost:8080/api/admin/invites \
  -H 'Authorization: Bearer замените-на-ваш-HKC_ADMIN_TOKEN' \
  -H 'Content-Type: application/json' \
  -d '{"expiresHours":24}'
```

Ответ содержит одноразовый `invite` и готовый `registrationUrl`. Получатель
открывает эту ссылку и придумывает собственные логин и пароль. Код можно
также вставить вручную через кнопку «У меня есть инвайт». После
регистрации инвайт удаляется. Пароль хранится только в виде bcrypt-хэша.

Сессия находится в `HttpOnly`/`SameSite=Strict` cookie и живёт 30 дней либо
до перезапуска сервера. Перезапуск не удаляет пользователя — потребуется
только войти заново.

Инвайт выдаётся оператору или наблюдателю. Оператор может запускать и
останавливать бота; наблюдатель видит состояние системы и журнал.
Владелец административного токена меняет роли в админке. Ранее созданные
пользователи автоматически считаются операторами.

В основной панели доступны обзор, журнал с фильтрами и экспортом, единый экран
ресурсов WSL/Linux (CPU, общая RAM, диск, load average и uptime), диагностика
установки, светлая тема и быстрые действия `Ctrl+K`. Память процесса остаётся
в краткой сводке на главном экране. Счётчики ошибок относятся к последним 1000
строкам лога, а не ко всей истории.

Если задан `HKC_WEBHOOK_URL`, сервер каждые 15 секунд проверяет состояние
бота и отправляет JSON вида `{"service":"Heroku bot","status":"running",
"time":"..."}` при изменении состояния. URL должен использовать HTTPS.
Для публичной страницы статуса установите `HKC_PUBLIC_STATUS=1`; по умолчанию
она не раскрывает состояние сервиса.

## Административная панель

Откройте <http://localhost:8080/admin/> и введите `HKC_ADMIN_TOKEN`. Панель
показывает зарегистрированных пользователей, дату регистрации, количество
активных сессий, последнюю активность и состояние онлайн. Пользователь
считается онлайн, если обращался к серверу за последние 30 секунд.

Там же можно создавать и отзывать инвайты, копировать готовые ссылки
регистрации и удалять пользователей. При удалении пользователя все его
текущие сессии немедленно завершаются. Административный токен хранится
только в `sessionStorage` вкладки и удаляется кнопкой «Закрыть сессию».

Раздел «Резервные копии доступа» сохраняет базу пользователей и инвайтов в
`backups/` рядом с `HKC_AUTH_FILE`. Перед восстановлением создаётся ещё одна
копия текущей базы, а после восстановления завершаются все пользовательские
сессии. Копии содержат хэши паролей и действующие инвайты, поэтому каталог
нужно защищать как секрет.

Настройки бота не редактируются в админке. Существующий `config.json` в
`HEROKU_DIR` остаётся без изменений; служебный API для совместимости сохранён.

«Проверка Heroku» в админке запускает четыре готовые диагностики: сведения о
процессе, стартовый лог, состояние Git и версию Python. Ниже находится WSL-консоль
для произвольных команд. Они выполняются через `/bin/sh` в `HEROKU_DIR` с правами
пользователя службы панели, ограничены 30 секундами и 64 КиБ вывода. Каждое
выполнение фиксируется в аудите, но текст команды туда не записывается, чтобы не
сохранять возможные секреты. Доступ к консоли равносилен shell-доступу к серверу,
поэтому административный токен и HTTPS особенно важны.

Управление API-токенами убрано из админки. Уже выпущенные токены продолжают
работать, а служебный API сохранён для совместимости. В базе хранится SHA-256
хэш. Токен передаётся
в заголовке `Authorization: Bearer hkc.…`. Доступные маршруты:
`GET /api/v1/status`, `GET /api/v1/logs`, `POST /api/v1/bot/start|stop|restart`.
Токен `read` не может управлять ботом. Отозванный токен перестаёт работать сразу.

История действий показывает последние 100 событий; файл `audit.jsonl`
автоматически удерживает не более 1000 последних записей.

## Обновления панели и сверка исходников

Панель в WSL запускается службой `hkc-web.service`: для ручного перезапуска
используйте `sudo systemctl restart hkc-web.service`. Команда `pkill hkc-web;
./bin/hkc-web` запускает старую сборку вне службы и без настроек обновления.
Служба автоматически поднимает панель после неожиданного завершения процесса.

В админке раздел «Обновления и сверка» сопоставляет четыре состояния: версию
запущенного бинарника, Git-копию сервера, дополнительную локальную копию и
последний стабильный GitHub Release. Отдельно отображается коммит GitHub main.
Проверка выполняется каждые 10 минут и не требует GitHub-токена. Ошибки сети
показываются как ошибки проверки, а не как отсутствие обновлений.

Кнопка обновления открывает отдельное окно. Там показываются текущая и целевая
версии, готовность к установке, прогресс и журнал безопасных этапов. Окно
переподключается после перезапуска сервера. Админка организована в раскрываемые
ветви; состояние ветвей сохраняется в браузере. Повторяющиеся действия в истории
сгруппированы и раскрываются по нажатию. Показаны группы из последних 100
событий, на сервере удерживается не более 1000 отдельных записей.

Установка запускается только кнопкой администратора. Поддерживается Linux amd64
под systemd. Переменные `HKC_SOURCE_DIR` и `HKC_LOCAL_SOURCE_DIR` указывают на
копии репозитория, `HKC_UPDATE_DIR` — на каталог состояния и резервных сборок,
`HKC_UPDATE_ENABLED=1` включает кнопку установки. Если дополнительная локальная
копия не задана, она помечается как неподключённая. `HKC_ADMIN_TOKEN_FILE` позволяет
читать существующий административный токен из защищённого файла.

Служба `hkc-update.service` работает независимо от панели: скачивает стабильный
релиз из фиксированного репозитория, проверяет SHA-256 архива, безопасную структуру
архива и версию/коммит внутри бинарника. Предыдущий бинарник остаётся в
`HKC_UPDATE_DIR/backups`. После атомарной замены служба перезапускает панель и
проверяет `/api/version`; при неудаче возвращает предыдущий бинарник. Только
после успешного запуска исходники продвигаются через `git merge --ff-only`.
Незакоммиченные файлы, другая ветка или расходящаяся история блокируют установку.
Пользовательские базы, инвайты, токены, логи и каталог бота не заменяются.

Файлы в `deploy/` содержат службы, установщик и тесты отката. `install_wsl.py`
предназначен для существующей установки `/root/heroku-console` на этом ПК:
сохраняет её текущие параметры и проверяет старый административный токен,
затем переводит запуск на systemd. Перед миграцией можно выполнить
`python3 deploy/install_wsl.py --binary /путь/к/проверенной/сборке --check-only`.
Другие установки должны адаптировать абсолютные пути служб и защищённый
`/etc/hkc/hkc.env`. Не публикуйте этот файл: он содержит параметры авторизации.

Для ручного возврата сохраните текущий бинарник, остановите `hkc-web.service`,
скопируйте выбранную резервную сборку в `bin/hkc-web` с правами `0755` и запустите
службу снова. Сверка покажет отличие бинарника от исходников; исходники при этом
не откатываются разрушительными Git-командами.

Пути мигратора не привязаны к конкретному компьютеру. Основной checkout задаётся
через `--source` (по умолчанию `/root/heroku-console`), а необязательная вторая
копия — через `--local-source`. Вместо аргументов можно использовать
`HKC_SOURCE_DIR` и `HKC_LOCAL_SOURCE_DIR`:

```sh
python3 deploy/install_wsl.py \
  --binary /путь/к/проверенной/сборке \
  --source /путь/к/hrk-console \
  --local-source /необязательная/вторая/копия \
  --check-only
```

Веб-служба запускается от владельца каталога `--source`; другую отдельную
учётную запись можно выбрать через `--service-user hkc` или
`HKC_SERVICE_USER=hkc`. У этой записи должны быть права
на чтение исходников и чтение/запись `HEROKU_DIR`, `HKC_AUTH_FILE` и каталога с
ним. Служба обновления остаётся отдельной root-службой, а установщик создаёт
для пользователя панели узкое правило sudo только на её запуск. Административный shell
по умолчанию отключён; для осознанного включения задайте
`HKC_TERMINAL_ENABLED=1`.

## HTTPS-доступ

Не открывайте порт `8080` напрямую и не публикуйте сервер по обычному HTTP.
Оставьте его на `127.0.0.1:8080`, а наружу выводите через HTTPS reverse proxy
на том же узле. Чтобы принимать `X-Forwarded-Proto: https` только от локального
proxy, задайте `HKC_TRUST_PROXY=1`; без этого флага заголовок не считается
доверенным.
