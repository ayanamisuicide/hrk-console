# Устройство проекта

Всё завязано на одном факте: **сам бот ничего не знает про консоль**. Это обычный процесс `python3 -m heroku`, который пишет `heroku.log` и живёт своей жизнью — hkc и GUI лишь читают этот файл и управляют процессом извне, без какого-либо API у бота.

TUI (`cmd/hkc` + `internal/tui`) и GUI (`gui/`) — две независимые витрины поверх одних и тех же пакетов. У каждой свой способ рисовать, но факты о боте они получают из одного места, поэтому и ведут себя одинаково.

| Путь | Назначение |
| --- | --- |
| `cmd/hkc` | Точка входа: разбор аргументов, автонастройка, проверки, меню, режимы |
| `botproc` | Процесс бота: поиск в `/proc`, запуск, остановка, аптайм, версия |
| `logfeed` | Разбор `heroku.log`, правила видимости, слежение за файлом |
| `setup` | Автонастройка окружения, доустановка зависимостей модулей |
| `state` | Настройки экрана между запусками — общие для TUI и GUI |
| `preflight` | Проверки окружения (сами проверки, без экрана) — общие для TUI и GUI |
| `selfupdate` | Проверка версии на GitHub и подмена себя — общие для TUI и GUI |
| `internal/tui` | Экраны на Bubble Tea |
| `internal/theme` | Палитра и стили — перекрашивать TUI нужно здесь |
| `internal/termwin` | Открытие окна терминала для режима «два окна» |
| `gui/` | Нативное окно на Wails — отдельный Go-модуль |

`botproc`, `logfeed`, `setup`, `state`, `preflight` и `selfupdate` лежат вне `internal/` намеренно: это чистый Go без завязки на терминал, и его переиспользует `gui`. Go не пускает `internal/*` за пределы дерева модуля, поэтому TUI-специфика (сами экраны на Bubble Tea) остаётся под `internal/`, а общая логика — нет.

Путь `hkc` без аргументов: `main()` → `setup.EnsureAll` → экран проверок → меню → один из `modeAttach`/`modeRestart`/`modeTwoWindows`/`modeStop` → `internal/tui.Viewer`. GUI делает то же самое в одном окне: `gui/app.go` поднимает `botproc`, `logfeed` и `state` сразу при старте.

## cmd/hkc

`--version`/`--help` отвечают раньше всего остального — до входа в Bubble Tea, чтобы работать и там, где нет терминала (скрипт, ssh, сборщик пакетов).

`hkc console` — путь в обход меню: запускает бота в текущем терминале с унаследованным `stdin`/`stdout`/`stderr` (`botproc.RunForeground`), единственный режим с интерактивным вводом. Его использует режим «два окна», и он же годится для первого входа в аккаунт.

`hkc update` — тоже в обход меню (и в обход автонастройки с проверками: версия hkc не имеет отношения к тому, поднят ли venv бота), запускает `tui.UpdateScreen`. Тот же путь доступен из меню пунктом 5 — в этом случае после экрана управление возвращается в меню, а не завершает программу.

## botproc

Знает о боте ровно то, что можно вычитать из `/proc`. `PIDs()`/`PID()`/`Alive()` сканируют `/proc/*/cmdline` на подстроку `"python3 -m heroku"`.

`Start()` поднимает бота в собственной сессии (`Setsid`) командой `bash -c "source venv/bin/activate && exec python3 -m heroku"`; вывод уходит в `.startup.log`, `stdin` не подключён — поэтому и нужен разовый ручной вход. `flock` на `.launch.lock` не даёт двум окнам стартовать бота одновременно.

`Stop()` — `SIGTERM` и до 5 секунд ожидания, затем `SIGKILL`. `Uptime()` считается из `/proc/<pid>/stat` и `/proc/uptime`, без внешнего `ps`. `Version()` берёт номер из последнего баннера в хвосте лога.

## logfeed

`parse.go` — построчный парсер: заголовок с `[LEVEL]` может тянуть за собой продолжение или трейсбек (строка без заголовка приезжает «жёстким переносом» предыдущей записи). `SameEntry` решает, схлопывать ли повтор — по уровню, модулю и тексту, но не по продолжениям: одинаковые кадры рекурсии в трейсбеке не повтор одного события. `Visible` совмещает три независимых правила — порог по важности, `showDebug` и фильтр (подстрока или `re:`-регэксп; битый шаблон трактуется как «не совпало», а не паника).

`tail.go` — собственная замена `tail -F`: опрашивает файл каждые 250мс, переживает ротацию и обрезание на месте, не отдаёт недописанную половину строки (бот пишет не атомарно) и умеет сказать *почему* не читается, а не просто молча замолчать.

## setup

`EnsureAll` идёт по цепочке: клонировать `~/Heroku` → `python3`/`python3-venv` → `venv` + `requirements.txt` → эмулятор терминала → `ffmpeg`. Каждый шаг проверяет, не сделано ли уже. Ставит через `sudo apt-get` — рассчитан на Debian/Ubuntu-семейство.

`deps.go` решает отдельную задачу: зависимости **загруженных модулей бота**, про которые `requirements.txt` не знает. Питоновский скрипт запускается через `venv/bin/python` бота и через `ast.parse` (не regex — закомментированный `import` не должен считаться зависимостью) собирает импорты `loaded_modules/*.py` и заголовки `# requires:`, отсеивает уже установленное и то, что загрузчик подменяет на лету (`telethon`/`hikkatl` → `herokutl`), переводит расхождения импорт↔пакет (`PIL`→`pillow`) и ставит каждый пакет отдельным `pip install` — одна промашка не должна ронять остальные. Что не встало, попадает в `.hkc-failed-deps.json` и не пробуется повторно сутки.

## preflight

Восемь проверок: каталог бота, файл лога, `venv`, `python3`, `ffmpeg`, зависимости модулей, права на запись, модульные тесты. Тесты гоняются `go test -count=1 -json ./...` по пути к исходникам, вшитому при сборке (`-X heroku-console/preflight.repoRoot=`) — без этого у консоли из `~/.local/bin` они не запускались бы никогда.

Изначально жил под `internal/`, пока им пользовался только TUI. Как только тот же экран понадобился GUI (отдельный Go-модуль, `internal/*` ему структурно недоступен), пакет переехал на верхний уровень — тот же путь, которым раньше прошли `botproc`/`logfeed`/`setup`/`state`.

## selfupdate

Общая для hkc и GUI логика самообновления: `Check(current)` сравнивает версию с последним релизом на GitHub (`Available`/`OK` разведены — "нашлась новее" и "проверка отработала" разные вопросы, иначе вызывающему было бы не отличить "сети нет" от "и так последняя"), `Apply(assetPrefix, assetSuffix)` качает архив нужной витрины (`hkc-*` или `hrk-console-gui-*` — обе лежат в одном релизе) и атомически (`os.Rename` в пределах одной ФС) подменяет им себя на диске. Раньше жил только в `gui/app.go` — TUI обновлялся вручную, `git pull && make install`.

## internal/tui

`menu.go` (выбор режима с живым PID/аптаймом), `preflight.go` (анимированная обёртка вокруг проверок), `update.go` (самообновление: проверка → явное "обновить" → явное "перезапустить", тот же двухшаговый контракт, что и у GUI-бейджа), `viewer.go` (живой лог, вотчдог, поиск), `sidebar.go` (модули с градиентными барами, sparkline, счётчики), `render.go` (колонки, рамка, оверлеи), `screen.go` (блоки экрана — схлопывание повторов, позиции проблем, зебра).

Вьюер держит кольцевой буфер сырых строк на 5000 записей — достаточно, чтобы при смене фильтра пересобрать экран из истории, а не только из новых строк. Вотчдог (`a`) выключен по умолчанию: режим «Подключиться, не трогая процесс» не должен трогать процесс без явного согласия.

## internal/theme

Один источник цвета на весь TUI, палитра в духе btop/htop. `Gradient()` красит рамку перетеканием акцент→фон через Lab-пространство. `MeterBar()` — столбик градиентом зелёный→жёлтый→красный по заполненной доле. `Sparkline()` — восемь уровней блочных символов.

## internal/termwin

Перебирает эмуляторы по порядку: `ghostty`, `kitty`, `alacritty` (гибкая раскраска), затем штатные терминалы окружений Mint (`gnome-terminal`, `mate-terminal`, `xfce4-terminal`), последним — `x-terminal-emulator`. Если ничего не нашлось, `cmd/hkc` откатывается на запуск в текущем терминале.

## state

Четыре поля (`ShowDebug`, `ShowSidebar`, `MinLevel`, `Watchdog`) в `~/.config/hkc/state.json`. Любая ошибка чтения тихо откатывается на значения по умолчанию — настройки экрана не стоят того, чтобы ронять запуск. Файл общий у TUI и GUI.

## gui/

Отдельный Go-модуль внутри репозитория, подключающий корневые пакеты через `replace heroku-console => ../`. `app.go` держит `botproc.Manager`, парсер и буфер записей под мьютексом; при старте окна загружает `state`, поднимает историю и запускает горутины — живой хвост лога, статус раз в секунду, разовая проверка обновлений и прогон `preflight`. Методы, вызываемые из JS, — обычные Go-методы, обвязку Wails генерирует сам.

Экран проверок перед стартом — те же восемь проверок `preflight.All`, что у TUI, тем же контрактом (по одной, не разом). `runPreflight` шлёт результат каждой отдельным событием (`preflight-check`), а не одним ответом в конце: «модульные тесты» внутри могут идти секундами, и окно не должно молчать всё это время. Идёт параллельно с загрузкой истории лога, не блокируя её — сама проверка окружения не условие для того, чтобы начать читать уже существующий `heroku.log`. `PreflightChecks()` отдаёт только имена (без запуска) — фронтенду нужно нарисовать полный список строк раньше, чем придёт первое событие.

`CheckForUpdate`/`ApplyUpdate` — тонкие обёртки над `selfupdate.Check`/`selfupdate.Apply`: сама логика запроса к GitHub, сравнения версий и подмены бинарника общая с TUI, GUI лишь добавляет своё имя архива (`hrk-console-gui-*`) и раскладывает результат по полям для JSON.

Вотчдог здесь — зеркало TUI-вотчдога с одним отличием: GUI-окно тикает всегда, даже когда бот не запущен (TUI входит во вьюер только когда бот уже жив), поэтому вотчдог «вооружается» лишь после того, как хоть раз застал бота живым — иначе на свежем окне с сохранённым `auto-restart` он путал бы «ещё не поднят» с «упал» (починено в `v1.6.1`).

Фронтенд — vanilla JS без фреймворка: DOM строится один раз, дальше точечные обновления. Приём строк батчится через `requestAnimationFrame` кусками по 300 — построчная запись `scrollTop` давала forced reflow и подвисание на всплеске из сотен строк.

## CI и релизы

`ci.yml` — на каждый push в `main` и каждый PR: `gofmt -l`, `go vet`, `go test -count=1 -race`, `make build`.

`release.yml` — по тегу `v*`: те же проверки, сборка, архив `hkc-<тег>-linux-amd64.tar.gz`, тело релиза вырезается `awk`-ом из `CHANGELOG.md` по секции версии — то, что видно на странице релиза, и то, что в репозитории, не могут разойтись.

## Makefile

`VERSION` из `git describe --tags --dirty` — сборка из грязного дерева получает суффикс. `CGO_ENABLED=0`: проект не использует cgo, но `go build` включает его сам при наличии `gcc` в `PATH`, и без заголовков libc сборка падает на `runtime/cgo`. `LDFLAGS` вшивает версию и путь к исходникам для `preflight`.
