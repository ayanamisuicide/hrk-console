# Устройство проекта

Всё завязано на одном факте: **сам бот ничего не знает про консоль**. Это обычный процесс `python3 -m heroku`, который пишет `heroku.log` и живёт своей жизнью — hkc и GUI лишь читают этот файл и управляют процессом извне, без какого-либо API у бота.

TUI (`cmd/hkc` + `internal/tui`) и GUI (`gui/`) — две независимые витрины поверх одних и тех же пакетов. У каждой свой способ рисовать, но факты о боте они получают из одного места, поэтому и ведут себя одинаково.

| Путь | Назначение |
| --- | --- |
| `cmd/hkc` | Точка входа: разбор аргументов, автонастройка, проверки, меню, режимы |
| `botproc` | Процесс бота: поиск в `/proc`, запуск, остановка, аптайм, версия |
| `logfeed` | Разбор `heroku.log`, правила видимости, слежение за файлом |
| `setup` | Автонастройка окружения, доустановка зависимостей модулей |
| `state` | Настройки экрана между запусками — общие для TUI и GUI |
| `preflight` | Проверки окружения (сами проверки, без экрана) — общие для TUI и GUI |
| `selfupdate` | Проверка версии на GitHub и подмена себя — общие для TUI и GUI |
| `remotebot` | То же, что `botproc`/`logfeed`, но по SSH — бот на другой машине |
| `internal/tui` | Экраны на Bubble Tea |
| `internal/theme` | Палитра и стили — перекрашивать TUI нужно здесь |
| `internal/termwin` | Открытие окна терминала для режима «два окна» |
| `gui/` | Нативное окно на Wails — отдельный Go-модуль |

`botproc`, `logfeed`, `setup`, `state`, `preflight` и `selfupdate` лежат вне `internal/` намеренно: это чистый Go без завязки на терминал, и его переиспользует `gui`. Go не пускает `internal/*` за пределы дерева модуля, поэтому TUI-специфика (сами экраны на Bubble Tea) остаётся под `internal/`, а общая логика — нет.

Путь `hkc` без аргументов: `main()` → `setup.EnsureAll` → экран проверок → меню → один из `modeAttach`/`modeRestart`/`modeTwoWindows`/`modeStop` → `internal/tui.Viewer`. GUI делает то же самое в одном окне: `gui/app.go` поднимает `botproc`, `logfeed` и `state` сразу при старте.

## cmd/hkc

`--version`/`--help` отвечают раньше всего остального — до входа в Bubble Tea, чтобы работать и там, где нет терминала (скрипт, ssh, сборщик пакетов).

`hkc console` — путь в обход меню: запускает бота в текущем терминале с унаследованным `stdin`/`stdout`/`stderr` (`botproc.RunForeground`), единственный режим с интерактивным вводом. Его использует режим «два окна», и он же годится для первого входа в аккаунт.

`hkc update` — тоже в обход меню (и в обход автонастройки с проверками: версия hkc не имеет отношения к тому, поднят ли venv бота), запускает `tui.UpdateScreen`. Тот же путь доступен из меню пунктом 5 — в этом случае после экрана управление возвращается в меню, а не завершает программу.

## botproc

Знает о боте ровно то, что можно вычитать из `/proc`. `PIDs()`/`PID()`/`Alive()` сканируют `/proc/*/cmdline` на подстроку `"python3 -m heroku"`.

`Start()` поднимает бота в собственной сессии (`Setsid`) командой `bash -c "source venv/bin/activate && exec python3 -m heroku"`; вывод уходит в `.startup.log`, `stdin` не подключён — поэтому и нужен разовый ручной вход. `flock` на `.launch.lock` не даёт двум окнам стартовать бота одновременно.

`Stop()` — `SIGTERM` и до 5 секунд ожидания, затем `SIGKILL`. `Uptime()` считается из `/proc/<pid>/stat` и `/proc/uptime`, без внешнего `ps`. `Version()` берёт номер из последнего баннера в хвосте лога.

`Start`/`Stop`/`RunForeground` — за `//go:build linux` (`manage_linux.go`, `console.go`): используют `syscall.Kill`/`Flock`/`Setsid`, которых нет на других ОС. `manage_other.go`/`console_other.go` (`//go:build !linux`) — рабочие заглушки с той же сигнатурой, возвращают понятную ошибку вместо отказа собраться. Понадобилось, когда GUI научился собираться под Windows (см. `gui/`, `remotebot`) — без этого разделения пакет `botproc`, а с ним и весь `gui`, не компилировался бы под `GOOS=windows` вовсе. Остальные функции (`PIDs`/`PID`/`Alive`/`AliveAt`/`Uptime`/`Version`) уже были обычным `os.ReadFile`/`os.ReadDir` без привязки к ОС — их разделять не потребовалось, на не-Linux они просто ничего не находят.

## logfeed

`parse.go` — построчный парсер: заголовок с `[LEVEL]` может тянуть за собой продолжение или трейсбек (строка без заголовка приезжает «жёстким переносом» предыдущей записи). `SameEntry` решает, схлопывать ли повтор — по уровню, модулю и тексту, но не по продолжениям: одинаковые кадры рекурсии в трейсбеке не повтор одного события. `Visible` совмещает три независимых правила — порог по важности, `showDebug` и фильтр (подстрока или `re:`-регэксп; битый шаблон трактуется как «не совпало», а не паника).

`tail.go` — собственная замена `tail -F`: опрашивает файл каждые 250мс, переживает ротацию и обрезание на месте, не отдаёт недописанную половину строки (бот пишет не атомарно) и умеет сказать *почему* не читается, а не просто молча замолчать.

## setup

`EnsureAll` идёт по цепочке: клонировать `~/Heroku` → `python3`/`python3-venv` → `venv` + `requirements.txt` → эмулятор терминала → `ffmpeg`. Каждый шаг проверяет, не сделано ли уже. Ставит через `sudo apt-get` — рассчитан на Debian/Ubuntu-семейство.

`deps.go` решает отдельную задачу: зависимости **загруженных модулей бота**, про которые `requirements.txt` не знает. Питоновский скрипт запускается через `venv/bin/python` бота и через `ast.parse` (не regex — закомментированный `import` не должен считаться зависимостью) собирает импорты `loaded_modules/*.py` и заголовки `# requires:`, отсеивает уже установленное и то, что загрузчик подменяет на лету (`telethon`/`hikkatl` → `herokutl`), переводит расхождения импорт↔пакет (`PIL`→`pillow`) и ставит каждый пакет отдельным `pip install` — одна промашка не должна ронять остальные. Что не встало, попадает в `.hkc-failed-deps.json` и не пробуется повторно сутки.

## preflight

Восемь проверок: каталог бота, файл лога, `venv`, `python3`, `ffmpeg`, зависимости модулей, права на запись, модульные тесты. Тесты гоняются `go test -count=1 -json ./...` по пути к исходникам, вшитому при сборке (`-X heroku-console/preflight.repoRoot=`) — без этого у консоли из `~/.local/bin` они не запускались бы никогда.

Изначально жил под `internal/`, пока им пользовался только TUI. Как только тот же экран понадобился GUI (отдельный Go-модуль, `internal/*` ему структурно недоступен), пакет переехал на верхний уровень — тот же путь, которым раньше прошли `botproc`/`logfeed`/`setup`/`state`.

## selfupdate

Общая для hkc и GUI логика самообновления: `Check(current)` сравнивает версию с последним релизом на GitHub (`Available`/`OK` разведены — "нашлась новее" и "проверка отработала" разные вопросы, иначе вызывающему было бы не отличить "сети нет" от "и так последняя"), `Apply(assetPrefix, assetSuffix)` качает архив нужной витрины (`hkc-*` или `hrk-console-gui-*` — обе лежат в одном релизе). Раньше жил только в `gui/app.go` — TUI обновлялся вручную, `git pull && make install`.

Подмена себя на диске — единственное место в пакете, зависящее от ОС, через обычный `if runtime.GOOS == "windows"`, а не build-теги (сама ветка небольшая, заводить два файла ради неё было бы лишним): на Linux `Apply` подменяет себя атомарно и сразу (`os.Rename` поверх открытого работающего файла там безопасен). На Windows так нельзя — файл образа заблокирован, пока процесс из него выполняется, — поэтому `Apply` кладёт новую версию рядом (`exe+".new"`, см. `StagedPath`/`PendingUpdate`), а настоящую подмену и перезапуск делает вызывающая сторона уже после того, как этот процесс завершится (`gui/restartswap_windows.go`).

## remotebot

То же самое, что `botproc`+`logfeed` делают локально (найти pid бота, старт/стоп, аптайм, версия, хвост и живое слежение за `heroku.log`), но когда бот живёт на другой машине, а GUI — на этой. На удалённой стороне ничего не разворачивается: команды идут обычным SSH-exec (`golang.org/x/crypto/ssh`) — поиск по `/proc` через `for p in /proc/[0-9]*`, `kill`, `tail -c +N` — тем же способом, каким это делал бы человек в терминале. Сознательный выбор, а не временное решение: отдельный агент или сборка `hkc` под версию Go, которая может не совпадать с той, что стоит на удалённой машине, — лишняя движущаяся часть ради того, что и так делается несколькими командами оболочки.

Поиск pid — по НАЧАЛУ `/proc/<pid>/cmdline`, не по вхождению где угодно: SSH выполняет сам сканирующий скрипт как `bash -c '<весь текст скрипта>'`, и текст скрипта тоже содержит искомую строку — поиск подстрокой находил сам себя, pid в окне GUI дёргался на каждый опрос. `PIDs()` дополнительно сортирует результат численно — шелл перебирает `/proc/[0-9]*` в лексикографическом порядке ("1000" раньше "999"), без сортировки при нескольких найденных процессах на экран мог попасть то один, то другой (тот же приём и в `botproc.PIDs()`).

`Start()` — `flock` на `.launch.lock` не даёт двум окнам стартовать бота одновременно; критично, чтобы сам бот, будучи выпущен через `setsid`, не наследовал держащий лок дескриптор (`9>&-` в команде запуска) — иначе он держал бы замок всю свою жизнь, и любой следующий `Start()` без предварительного `Stop()` (второе окно, вотчдог) получал бы «занято» вместо честного «уже запущен».

`Follow()` — не `tail -F` на удалённой стороне (пришлось бы отдельно убирать зависший процесс при отключении), а поллинг с локальной стороны раз в 250мс: `stat` + `tail -c +offset` одной SSH-командой на попытку, тот же приём и тот же интервал, что у `logfeed.Follow` локально, включая обработку ротации/обрезания файла.

Ключ хоста — TOFU (Trust On First Use): `Dial` при первом подключении к хосту молча запоминает его ключ в файл (`known_hosts`, свой, не системный `~/.ssh/known_hosts`), при следующих — сверяет. Несовпадение уже запомненного ключа не принимается автоматически никогда — это ровно то, от чего защищает проверка ключа хоста.

## internal/tui

`menu.go` (выбор режима с живым PID/аптаймом), `preflight.go` (анимированная обёртка вокруг проверок), `update.go` (самообновление: проверка → явное "обновить" → явное "перезапустить", тот же двухшаговый контракт, что и у GUI-бейджа), `viewer.go` (живой лог, вотчдог, поиск), `sidebar.go` (модули с градиентными барами, sparkline, счётчики), `render.go` (колонки, рамка, оверлеи), `screen.go` (блоки экрана — схлопывание повторов, позиции проблем, зебра).

Вьюер держит кольцевой буфер сырых строк на 5000 записей — достаточно, чтобы при смене фильтра пересобрать экран из истории, а не только из новых строк. Вотчдог (`a`) выключен по умолчанию: режим «Подключиться, не трогая процесс» не должен трогать процесс без явного согласия.

## internal/theme

Один источник цвета на весь TUI, палитра в духе btop/htop. `Gradient()` красит рамку перетеканием акцент→фон через Lab-пространство. `MeterBar()` — столбик градиентом зелёный→жёлтый→красный по заполненной доле. `Sparkline()` — восемь уровней блочных символов.

## internal/termwin

Перебирает эмуляторы по порядку: `ghostty`, `kitty`, `alacritty` (гибкая раскраска), затем штатные терминалы окружений Mint (`gnome-terminal`, `mate-terminal`, `xfce4-terminal`), последним — `x-terminal-emulator`. Если ничего не нашлось, `cmd/hkc` откатывается на запуск в текущем терминале.

## state

Четыре поля (`ShowDebug`, `ShowSidebar`, `MinLevel`, `Watchdog`) плюс `Remote` (хост/пользователь/ключ/каталог для `remotebot`, актуально только GUI — TUI всегда на той же машине, что и бот) в `~/.config/hkc/state.json`. Любая ошибка чтения тихо откатывается на значения по умолчанию — настройки экрана не стоят того, чтобы ронять запуск. Файл общий у TUI и GUI; `Remote.Host` пустой — тот же смысл, что и раньше у всего файла: обычный локальный режим.

## gui/

Отдельный Go-модуль внутри репозитория, подключающий корневые пакеты через `replace heroku-console => ../`. `app.go` держит `botproc.Manager`, парсер и буфер записей под мьютексом; при старте окна загружает `state`, поднимает историю и запускает горутины — живой хвост лога, статус раз в секунду, разовая проверка обновлений, прогон `preflight` и попытку поднять трей. Методы, вызываемые из JS, — обычные Go-методы, обвязку Wails генерирует сам.

`tray.go`/`traymenu.go` — системный трей напрямую по D-Bus (протокол StatusNotifierItem), без cgo и GTK-библиотек трея: в 1.8.0 от него отказались именно из-за них (обычные Go-обёртки тянут cgo+libappindicator, а GNOME без расширения такой индикатор не показывает вовсе). Сам протокол слушают и appindicator-расширение GNOME, и нативные лотки Cinnamon/MATE/Xfce — основные окружения Mint (см. `internal/termwin`) — поэтому подключение к нему напрямую снимает зависимость от cgo целиком. Best-effort и без повторов: если сессионной шины нет или наблюдателя (`StatusNotifierWatcher`) никто не поднял, `Tray.Start` молча отступает, тем же приёмом, что и `notifyDesktop`. Меню — минимальная, но настоящая реализация `com.canonical.dbusmenu` (два пункта: переключить окно, выйти), без вложенности и без интроспекции: хосты трея реализуют фиксированный протокол по спецификации, а не спрашивают интроспекцию о том, как вызывать `Activate`/`GetLayout`. Проверено тестами против настоящего `dbus-daemon` (`tray_test.go`), а не только сборкой — то, чего не хватало прежней (не сделанной) попытке.

Собирается и под Linux, и под Windows (`wails build -platform windows/amd64` — тот же исходный код, без отдельной ветки; кросс-платформенность обеспечивает разделение `botproc` по build-тегам, см. выше). Локальный бот (`botproc`) и удалённый (`remotebot`) — за одним и тем же набором точек подмены на `App` (`pid`/`aliveAt`/`start`/`stop`/`uptime`/`botVersion`): `NewApp` изначально наводит их на локальный `botproc`, `startRemote` (если в `state.Remote.Host` что-то есть) переставляет на `remotebot.Client` — дальше `statusLoop`, вотчдог и `StartBot`/`StopBot`/`RestartBot` работают одинаково, не зная разницы. Осечка подключения не роняет окно: точки подмены остаются локальными, которые на машине без `/proc` и без каталога бота просто ничего не находят молча, а notice в логе объясняет, что произошло.

`PreflightChecks()` (список для экрана проверок) смотрит на `a.ui.Remote.Host`, а не на `a.remote`: `a.ui` выставляется синхронно в начале `startup`, до всех горутин, а `a.remote` появляется только после успешного SSH-подключения — гонка между ними раньше иногда оставляла экран проверок зависшим с локальным списком, который в удалённом режиме никто не резолвит.

`TestRemoteConnection` — то же самое, что настоящее подключение (`remotebot.Dial`, включая TOFU-проверку ключа), но соединение сразу закрывается и ничего не сохраняется: способ проверить хост/логин/ключ до того, как сохранять настройки и перезапускать окно ради ошибки, которую можно было узнать раньше. `ConnectRemote`/`DisconnectRemote` сохраняют `state.Remote` и зовут `RestartApp` — переключение источника бота на лету было бы источником гонок между старыми и новыми горутинами, честный перезапуск процесса проще и надёжнее.

Экран проверок перед стартом — та же логика `runChecklist` (по одной, не разом, событие `preflight-check` на каждую), что в TUI, только список проверок зависит от режима: локально — восемь `preflight.All`, удалённо — семь через `remotebot.Client.Preflight()` (те же самые, только по SSH; «модульные тесты» намеренно не входит — та проверка про исходники самой консоли, не про бота на другой машине). Идёт параллельно с загрузкой истории лога, не блокируя её. `PreflightChecks()` отдаёт только имена (без запуска), причём в удалённом режиме — через пустой, ещё не подключённый `&remotebot.Client{}`: сами имена не зависят от того, есть ли уже живое SSH-соединение, а ждать его здесь означало бы копировать ту же гонку с `a.remote`, что и выше.

Индикатор связи в статус-строке отражает `Status.RemoteState` (`connecting`/`online`/`offline`, пусто — локальный бот), а не просто адрес: `a.pid`/`a.aliveAt` в удалённом режиме сами обновляют его при каждом опросе — отдельного пинга не нужно, живость и так спрашивается раз в секунду. Осечка SSH-запроса не отдаёт мгновенно pid 0: последний достоверный ответ считается годным `remoteStaleWindow` (15с) — иначе сетевая заминка на секунду выглядела бы как падение бота, а вотчдог пытался бы его «спасти».

`CheckForUpdate`/`ApplyUpdate` — тонкие обёртки над `selfupdate.Check`/`selfupdate.Apply`: сама логика запроса к GitHub, сравнения версий и подмены бинарника общая с TUI, GUI лишь добавляет своё имя архива (`hrk-console-gui-*`) и раскладывает результат по полям для JSON.

`CheckChannels` опрашивает оба канала разом через `selfupdate.CheckBoth` (два независимых запроса параллельно — последовательно худший случай складывал бы два десятисекундных таймаута в двадцать) и отдаёт их состояния как есть, без вердикта «новее». Вердикта нет потому, что между каналами он невыразим: внутри канала версии сравнимы (`VersionLess` для stable, равенство тегов для dev), а `dev-<sha>` и `vX.Y.Z` — нет, в хеше нет порядка. Единственный признак, по которому они сопоставимы, — `Release.PublishedAt`, его экран и показывает. `Offer` считается по равенству тега запущенной сборке, а не по «новее»: это утверждение верно всегда, в отличие от сравнения версий.

`ApplyUpdateFrom` добавляет к обновлению отчёт о ходе: `selfupdate.ApplyChannelProgress` дёргает колбэк на каждом своём шаге (`StageQuery`/`StageFind`/`StageDownload`/`StageUnpack`/`StageSwap`), а GUI пересылает их фронтенду событием `update-step`. Отдельная функция в `selfupdate`, а не новый аргумент у `ApplyChannel`, — отчёт нужен только GUI, `hkc update` и TUI обходятся строкой в конце, и `onProgress == nil` возвращает прежнее поведение до последнего вызова. Байты считает `countingReader`, вставленный ДО `gzip` (в `Content-Length` обещан объём сжатого потока, и считать надо именно его, иначе «скачано» перевалило бы за «всего») и ограниченный по частоте: без ограничения колбэк звался бы на каждый `Read`, десятки тысяч раз на пятимегабайтном архиве, и в webview это стало бы тем же потоком событий, каким когда-то был построчный вывод лога. Скачивание и распаковка закрываются вместе, после `io.Copy`: `tar` тянет из `gzip`, а тот из сети, поэтому «скачано» перестаёт расти ровно тогда, когда распаковано последнее, — закрывать их поодиночке значило бы отрапортовать о готовности, пока байты ещё едут (на это есть тест). Ошибка уезжает отдельным событием `update-failed`: окно живёт на потоке шагов, и оборвись он молча — там навсегда остался бы крутящийся шаг.

Вотчдог здесь — зеркало TUI-вотчдога с одним отличием: GUI-окно тикает всегда, даже когда бот не запущен (TUI входит во вьюер только когда бот уже жив), поэтому вотчдог «вооружается» лишь после того, как хоть раз застал бота живым — иначе на свежем окне с сохранённым `auto-restart` он путал бы «ещё не поднят» с «упал» (починено в `v1.6.1`).

Фронтенд — vanilla JS без фреймворка: DOM строится один раз, дальше точечные обновления. Приём строк батчится через `requestAnimationFrame` кусками по 300 — построчная запись `scrollTop` давала forced reflow и подвисание на всплеске из сотен строк.

Раскладка — шапка, статус-строка и лог во всю оставшуюся высоту, без постоянной боковой колонки. Постоянно видно только то, что нужно, не отрываясь от лога (живость бота, счётчики проблем, три самых шумных модуля, состояние связи); полный список модулей выпадает по клику из своего же сегмента статус-строки, настройка удалённого бота открывается модальным окном. Это осознанный откат от прежней панели справа: из пяти её секций четыре либо дублировали статус-строку слово в слово (проблемы, аптайм, подключение), либо не давали принять ни одного решения (спарклайн активности и часовая история warn/err), а единственная полезная — список модулей как фильтр — не стоила оверлея во весь экран с затемнением. Счётчики `warn`/`err` теперь живут ровно в одном месте, а не в трёх. Стилистика соответственно плоская: одна сплошная поверхность с разделителями в 1px вместо плавающих блюр-карточек, и никаких бесконечных анимаций — единственная оставшаяся (спиннер проверки в `preflight`) отражает реально идущий процесс и живёт ровно столько, сколько он длится.

## CI и релизы

`ci.yml` — на каждый push в `main` и каждый PR: `gofmt -l`, `go vet`, `go test -count=1 -race`, `make build`.

`release.yml` — по тегу `v*`: те же проверки, сборка `hkc` и Linux-GUI (`ubuntu-latest`, один job) и Windows-GUI (`windows-latest`, отдельный job, `needs: release` — ждёт, пока первый job создаст объект релиза, и просто добавляет к нему свой файл). Три архива: `hkc-<тег>-linux-amd64.tar.gz`, `hrk-console-gui-<тег>-linux-amd64.tar.gz`, `hrk-console-gui-<тег>-windows-amd64.tar.gz` — всегда `.tar.gz`, не `.zip`, даже для Windows: `selfupdate` сам распаковывает архив в Go (`archive/tar`+`compress/gzip`), одним и тем же кодом на любой ОС, второй формат не понадобился. Тело релиза вырезается `awk`-ом из `CHANGELOG.md` по секции версии — то, что видно на странице релиза, и то, что в репозитории, не могут разойтись.

## Makefile

`VERSION` из `git describe --tags --dirty` — сборка из грязного дерева получает суффикс. `CGO_ENABLED=0`: проект не использует cgo, но `go build` включает его сам при наличии `gcc` в `PATH`, и без заголовков libc сборка падает на `runtime/cgo`. `LDFLAGS` вшивает версию и путь к исходникам для `preflight`.
